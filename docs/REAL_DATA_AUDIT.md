# ExamGuard Real-World Data & Production Integration Audit

**Date**: 2026-11-07  
**Author**: Principal Software Architect & QA Lead  
**Scope**: Complete end-to-end audit of data paths, synthetic/mock dependencies, and production integration boundaries across ExamGuard.

---

## 1. Executive Summary

ExamGuard was originally built with dual-mode operational capabilities: a high-fidelity demonstration subsystem (seeded by `/api/v1/demo/*`) for walkthroughs, alongside a fully architected database-driven core. While the underlying models, relational schemas (33 tables), security rules, and algorithms are enterprise-grade, several operational surfaces previously allowed synthetic data and fallback mocks to masquerade as live production state:

1. **Dashboard Demo Ingestion**: The main administrative dashboard presented a prominent "Load Demo Data" mechanism that injected static records (`DEMO001`, `DEMO002`, `DEMO003`) directly into the active database without gating by environment.
2. **Biometric Provider Ambiguity**: While `UniFaceProvider` (RetinaFace + ArcFace + MiniFASNet) is fully implemented, the default `FACE_VERIFICATION_PROVIDER` setting was `"deterministic"`, returning static similarity scores without processing live facial geometry.
3. **Storage Fallback in Production**: When Cloudinary credentials were absent, the storage subsystem silently defaulted to local disk storage, which on containerized platforms (such as Railway) is ephemeral and loses enrolled photos upon container restarts.
4. **Development Authentication**: The frontend `AuthContext` allowed an `eg_token` URL query parameter to bypass Google/Firebase sign-in if `NEXT_PUBLIC_ENABLE_DEV_AUTH` was set, which could compromise a production build if misconfigured.
5. **Observability Placeholders**: Previous health endpoints returned static mock responses rather than genuinely verifying database connections, storage APIs, or neural inference models.

This document traces the exact data flow for every feature from the frontend client to persistent storage or external APIs, catalogues synthetic dependencies, and establishes the required remediation.

## 3. End-to-End Data Path Tracing

### A. Candidate Face Verification & Attendance
```
[Client Webcam Capture]
         │ (Base64 JPEG / Blob)
         ▼
[Frontend: /verify or /invigilator]
         │ POST /api/v1/identity-verifications/{id}/verify-face
         ▼
[FastAPI Router: identity_verifications.py]
         │ Dependency: require_role(OPERATOR, INVIGILATOR)
         │ Invigilator assignment check (exam_id, hall_id)
         ▼
[Service: identity_verification.py]
         │ Retrieve reference_face_url from PostgreSQL
         │ Download reference image bytes
         ▼
[Provider: UniFaceProvider (ONNX Runtime)]
         │ 1. RetinaFace: Detect face in reference (must be 1)
         │ 2. RetinaFace: Detect face in live capture (must be 1)
         │ 3. ArcFace: Extract 512-d embeddings
         │ 4. Cosine Similarity: Compute identity_match_score
         │ 5. MiniFASNet: Compute liveness score
         ▼
[Decision Engine: evaluate_evidence()]
         │ Match policy evaluation (thresholds: 0.68 / 0.52)
         │ Status: MATCH / NO_MATCH / INCONCLUSIVE
         ▼
[Persistence: PostgreSQL Transaction]
         │ 1. Save IdentityVerificationEvidence (signals, confidence, provider="uniface")
         │ 2. Update IdentityVerificationAttempt (status, decision, scores)
         │ 3. If MATCH: create EntryVerification(status=GRANTED)
         │ 4. If GRANTED: create AttendanceRecord(status=PRESENT) & AttendanceEvent
         ▼
[Response JSON → Frontend UI State]
```
**Integrity Requirement**: If `FACE_VERIFICATION_PROVIDER` is set to `deterministic` in production, the chain is broken because the AI perception produces synthetic evidence. In production, this call must invoke `UniFaceProvider` or fail cleanly with an HTTP 503 error.

### B. Hall Ticket OCR Processing
```
[User Upload: PDF or PNG Admit Card]
         │ Multipart form upload
         ▼
[API: POST /api/v1/documents/upload]
         │ Authenticated as OPERATOR or ADMIN
         ▼
[Storage Adapter: CloudinaryStorage]
         │ In Production: Upload to Cloudinary API → Secure HTTPS URL
         │ In Development: LocalStorage disk write
         ▼
[Persistence: PostgreSQL documents table]
         │ Saves file_name, file_url, file_size, mime_type, exam_id
         ▼
[OCR Worker: POST /api/v1/documents/{id}/process]
         │ Fetch document bytes
         │ Execute native Tesseract binary (TESSERACT_CMD)
         │ Parse structured fields: USN, Student Name, Exam Date, Subject Code
         ▼
[Persistence: extraction_results & extracted_fields]
         │ Save extracted raw text, bounding boxes, and per-field confidence
         ▼
[Reviewer Interface: /documents]
         │ Reviewer inspects uncertain fields (<60% confidence)
         │ Confirms candidate linkage to Student record
```
**Integrity Requirement**: The OCR subsystem must never return fabricated text. If Tesseract fails or file is unparseable, an extraction error must be recorded and presented to the reviewer.

### C. Admission Guidance Chatbot
```
[Student Inquiry in Natural Language]
         │ POST /api/v1/chatbot/query { query, session_id }
         ▼
[API: Public Rate-Limited Endpoint (30 req/min)]
         ▼
[Service: chatbot.py]
         │ 1. Text normalization & tokenization (stopword filtering)
         │ 2. Intent matching against KnowledgeBaseItem rows in DB
         │ 3. Compute token overlap, substring, and fuzzy SequenceMatcher score
         │ 4. Confidence >= 0.35 threshold check
         ▼
[Branching Logic]
         ├── If Matched:
         │      Retrieve authoritative answer, category, source citations
         │      Check requires_admin_confirmation flag
         └── If Unmatched (< 0.35 confidence):
                Return honest institutional fallback response
                Target: admissions@dscasc.edu.in / (080) 2666-2222
         ▼
[Persistence: chat_query_logs table]
         │ Log query_text, matched_intent, category, confidence, timestamp
         │ (Zero PII or credential logging)
         ▼
[Response JSON → Student Chat Transcript]
```
**Integrity Requirement**: The chatbot must never answer out-of-scope questions with fabricated claims. Dynamic numbers (fees, dates) must require administrative confirmation.

## 4. Identified Operational Deficiencies & Required Action Plan

1. **Environment Gate on Demo Endpoints**:
   - `backend/app/api/v1/demo.py`: Add startup and route-level validation. If `APP_ENV == "production"`, block all `/load` and `/reset` operations with HTTP 403.
2. **Production Cloudinary Hardening**:
   - `backend/app/storage/cloudinary.py`: Disallow silent local storage fallback when `APP_ENV == "production"`.
3. **Biometric Provider Enforcement**:
   - `backend/app/services/face_verification/factory.py`: Raise `RuntimeError` if `APP_ENV == "production"` and `FACE_VERIFICATION_PROVIDER != "uniface"`.
4. **Development Auth Shielding**:
   - `frontend/src/context/AuthContext.tsx`: Ensure `getDevToken()` returns `null` immediately whenever `process.env.NODE_ENV === "production"`.
5. **Real Observability & Readiness Endpoint**:
   - `backend/app/monitoring/production.py`: Replace dummy checks with real database `SELECT 1`, real Cloudinary configuration verification, and real inference engine status.
6. **Frontend Dashboard Real Data Gating**:
   - `frontend/src/app/dashboard/page.tsx`: Hide demo loading cards in production; display operational empty states when no exams exist.
